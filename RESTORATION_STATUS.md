## Approved next networking milestone: room codes and direct-first connections — 2026-10-24

The user now requests a small, long-term signaling/credential service and room-code joining, preferring minimal server information/load and avoiding TURN gameplay charges whenever a working direct route exists. **This promotes room codes from the deferred backlog into the next networking milestone.** Beta 8 now implements the staged connection coordinator on top of the Beta 6 room service and Beta 7 address discovery. Temporary provider credential issuance and physical-network acceptance remain open; configured TURN credentials are currently entered by players.

Required connection preference for each host–guest pair:

1. **Existing manual port forward / known direct endpoint**, including a suitable LAN address: try the encrypted native TCP/TLS path first. Do not scan ports, assume an unverified public endpoint works, or require a relay for this route.
2. **UPnP**, only with the host's explicit opt-in: map the host's selected TCP port and try that direct endpoint. Clean up mappings and failed/cancelled attempts. Skip promptly when disabled/unsupported; it cannot bypass every upstream NAT or replace firewall permission.
3. **Direct WebRTC using STUN/ICE NAT traversal**, including trickled candidates and appropriate LAN candidates. Start with no TURN URLs/allocations so a quick relay candidate cannot defeat the direct-first policy.
4. **TURN as fallback**, using authenticated, short-lived provider credentials only when earlier methods fail or exhaust a measured, bounded direct-attempt budget. Allow either host or guest to require a relay independently. Keep a visible path/status; report when no configured relay is available.

The user clarified that STUN may discover the public IPv4 address to advertise for a manually forwarded TCP listener. Use the discovered IP as a candidate with the separately configured external TCP port; never reuse STUN's UDP-mapped port for native TCP. UPnP can supply the router's external IP as well. Keep a manual override and verify the actual authenticated connection, since VPNs, multiple uplinks and upstream NAT can make the discovery unsuitable. Beta 7 supplies bounded native-address discovery; Beta 8 integrates it into room hosting when the host address is blank, while retaining manual overrides.

Speed is a requirement alongside low relay use: prepare the host listener and signaling state before guests join; use short bounded probes, immediate explicit-failure handling, trickle ICE and one overall deadline. Avoid waiting through the current 90-second WebRTC deadline for each method. Preparatory work may overlap, while route admission follows the preference above. Do not leave users waiting indefinitely to avoid a small relay charge. Beta 8 has explicit provisional stage/overall deadlines; measure median/tail setup times and tune them before claiming production reliability. Port forwarding describes reachability, not a guarantee of lower latency than direct UDP/WebRTC.

Use a small HTTPS/WebSocket signaling service with expiring in-memory rooms as the initial design. Host creates a room, shares its room name/code and password, and approves each guest's assigned island hero. The user explicitly requested custom room names such as `poopedpants123`; support those with collision handling and rate limits rather than treating a short name as a secret. A later generated-code option must use cryptographic randomness. The server forwards only bounded connection messages (direct endpoint/pin/access details, offers/answers/trickled ICE), room membership/heartbeats and temporary TURN credentials. It does not run AI, forward game actions/snapshots/chat, store islands or receive saves. It necessarily sees connection metadata such as participant network addresses; minimize retention and redact secrets/SDP/candidates from logs. Preserve manual invitations and service-free LAN/direct operation if the service is unavailable.

Require private host/control and reconnect capabilities separate from the human-readable code, room expiry, join/credential rate limits, message/room/member caps, protocol compatibility and cleanup. A short code alone must not grant control of an existing saved hero. Keep permanent provider API secrets server-side; issue bounded temporary credentials to approved session participants. Measure service traffic, relay egress and actual selected paths separately. Do not force relay-only ICE. On signaling loss, already established gameplay connections keep running; room discovery/rejoin may remain unavailable until signaling recovers.

A relay-to-direct upgrade may be attempted after conditions improve, but must use a deliberate ICE restart or authenticated transport replacement with a coherent resync/action-sequence handoff. Never attach two live links to the same hero, replay actions, discard progression or repeatedly interrupt play to chase a direct route. Automatic mid-session transport switching is a separate acceptance gate; do not promise that TURN can always be discarded after setup.
